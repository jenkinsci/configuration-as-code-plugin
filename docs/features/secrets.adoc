= Handling Secrets
:toc:
:toc-placement: preamble
:toclevels: 3

Almost every Jenkins instance defines credentials and other sensitive information, and JCasC offers ways to manage credentials and other sensitive information in the YAML configuration files.
This page describes the available options.

There are 4 ways to securely pass credentials in JCasC:

* Using credential provider plugins
* Passing secrets through variables
* External secret decryption (portable JWE encrypted secrets)
* Passing secrets through encrypted strings

== Using credential provider plugins

link:https://plugins.jenkins.io/credentials[Credentials Plugin] is a standard way to manage credentials in Jenkins.
This plugin offers the link:https://jenkins.io/doc/developer/extensions/credentials/#credentialsprovider[CredentialsProvider extension point] which might be used to use credentials from external sources.
Examples of available plugins:

* link:https://plugins.jenkins.io/kubernetes-credentials-provider[Kubernetes Credentials Provider]
* link:https://plugins.jenkins.io/aws-secrets-manager-credentials-provider[AWS Secrets Manager Credentials Provider]
* link:https://plugins.jenkins.io/azure-keyvault[Azure KeyVault]
* link:https://go.cloudbees.com/docs/cloudbees-core/cloud-secure-guide/cyberark/#cyberark-credentials-provider[CyberARK Credential Provider] (proprietary plugin offered by CloudBees)

When an external Credentials provider is configured in Jenkins through JCasC, there is no need to define credentials inside.
Jenkins will be able to take the credentials from external storage by ID:

```yaml
 - kubernetes:
      connectTimeout: 5
      containerCapStr: "10"
      credentialsId: "k8s-user-password"
      jenkinsUrl: "http://localhost:8080"

```

Using an external credentials source does **NOT** address all use-cases.
There are configurations inside Jenkins (e.g. proxy password) which use a low-level link:https://javadoc.jenkins-ci.org/hudson/util/Secret.html[hudson.util.Secret] engine. 
For this type of credentials other engines should be used, see below.

NOTE: Fields backed by `hudson.util.Secret` (for example SMTP authentication
passwords in the Mailer plugin or proxy passwords) do not accept a Jenkins
credential ID. These fields expect the secret value itself``.``

== Passing secrets through variables

Currently, you can provide initial secrets to JCasC that all rely on <key,value> substitution of strings in the configuration.
For example, `Jenkins: "${some_var}"`. 
Default variable substitution using the `:-` operator from `bash` is also available.
For example, `key: "${VALUE:-defaultvalue}"` will evaluate to `defaultvalue` if `$VALUE` is unset. 
To escape a string from secret interpolation, put `^` in front of the value. 
For example, `Jenkins: "^${some_var}"` will produce the literal `Jenkins: "${some_var}"`.
This escaping mechanism applies to all JCasC configuration values, not only secrets.

Example:

```yaml
tool:
  customTool:
    script: |
      echo "^${WORKSPACE}"
```

JCasC removes the leading ^ during processing, leaving the literal ${WORKSPACE} in the final configuration.

=== Additional variable substitution

If you need to read a secret from a file, or perform additional en/decoding of the secret prior to use, the following helpers are available:

- `base64`
- `readFile`
- `decodeBase64`
- `readFileBase64`
- `json`
- `trim`
- `decrypt`

Helpers can be combined to do multiple transformations. Examples:

- `${base64:${readFile:/secret/file.txt}}`: read the file -> base64-encode it
- `${base64:${readFile:${SECRET_FILE_PATH}}}`: expand the SECRET_FILE_PATH variable -> read the file -> base64-encode it

==== base64

Encodes the provided secret to base64.

Example:

`${base64:HELLO WORLD}` -> `SEVMTE8gV09STEQ=`

==== decodeBase64

Decodes the provided base64-encoded secret into a plain text string.

Example:

```
${decodeBase64:${ENV_VAR}}
```

`decodeBase64` (and its related `readFileBase64`) may be useful for the credential plugin or any other plugin that needs binary base64 encoding of a file. This might help when handling link:https://tools.ietf.org/html/rfc7292[a PKCS#12 certificate files] or passing an SSH key as an environment variable.

==== file

Alias for `readFile`.

Example:

```
${file:/secret/file.txt}
```

==== fileBase64

Alias for `readFileBase64`.

Example:

```
${fileBase64:/secret/certificate.p12}
```

==== readFile

Reads the secret from the specified file.

The file contents are returned as-is, including any trailing whitespace characters. If the target configuration expects the value without trailing whitespace, you can combine `readFile` with `trim`.

Example:

```
${readFile:/secret/file.txt}
```

Safe Password Example:

```
${trim:${readFile:/secret/file-user-password.txt}}
```

==== readFileBase64

Read the specified binary file into a base64 representation.

```
${readFileBase64:/secret/certificate.p12}
```

==== json

Parse the string secret as JSON, then extract the value for the specified `<key>`.

(An empty string is returned if the JSON secret does not contain `<key>`).

```
${json:<key>:${ENV_VAR}}
```

This can help in situations where the backend has the option to store JSON secrets, e.g. AWS Secrets Manager.

Example:

```
${json:username:${ENV_VAR}}
```

==== trim

Removes trailing whitespace characters (including newlines, spaces, and tabs) from the provided secret. Leading whitespace is preserved.

Example:

```
${trim:${readFile:/secret/passphrase.txt}}
```

==== decrypt

Decrypts an externally encrypted secret using JSON Web Encryption (JWE Compact Serialization).
See <<external-secret-decryption-jwe,External secret decryption (JWE)>> for comprehensive documentation on key generation, encryption, configuration, deployment, and failure behavior.

Example:

```
${decrypt:jwe:eyJraWQiOiJJd1pFaDZyQWdvZyIsImVuYyI6IkEyNTZHQ00iLCJhbGciOiJSU0EtT0FFUC0yNTYifQ.BYfE7IUK...d29MhLabvpRcL4il.0v7j_LSHx_Y4zWNmJrH4ibLteOgeO9UU1kU.OCRjbF3ppMjaQuPuUkmiJg}
```

=== Secret sources

In JCasC there is a link:https://jenkins.io/doc/developer/extensions/configuration-as-code/#secretsource[SecretSource extension point] which allows resolving variables passed to JCasC.
We can provide these initial secrets in the following ways:

- link:https://github.com/jenkinsci/aws-secrets-manager-secret-source-plugin[AWS Secrets Manager]
- link:https://github.com/jenkinsci/configuration-as-code-secret-ssm-plugin[AWS Systems Manager Parameter Store]
- link:https://github.com/jenkinsci/azure-keyvault-plugin#secretsource[Azure KeyVault]
- Docker Secrets
- Environment variables
- link:https://github.com/jenkinsci/hashicorp-vault-plugin[HashiCorp Vault]
- Kubernetes secrets

==== Docker secrets

Files on path `/run/secrets/${KEY}` will be replaced by `${KEY}` in the configuration. 
The base folder `/run/secrets` can be overridden by setting the environment variable `SECRETS`.
So this can be used as a file based secret, and not just docker secrets.

==== Kubernetes secrets

Logic is the same as for docker-secrets.
The secret needs to be mounted as a file to `/run/secrets/`, and then the filename can be used as the KEY.
For example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: secret-name
data:
  filename: {{ "encoded string" | b64enc }}
```

can be used from a pod containing

```yaml
containers:
- name: jenkins
  volumeMounts:
  - name: filename-secret
    mountPath: /run/secrets/filename
    subPath: filename
    readOnly: true
volumes:
- name: filename-secret
  secret:
    secretName: secret-name
```

as:

```yaml
- credentials:
    - string:
      id: "cred-id"
      secret: ${filename}
```

==== HashiCorp Vault Secret Source

Prerequisites: link:https://plugins.jenkins.io/hashicorp-vault-plugin[HashiCorp Vault plugin] v2.4.0+.

- The environment variable `CASC_VAULT_PW` must be present, if token is not used and appRole/Secret is not used. (Vault password.)
- The environment variable `CASC_VAULT_USER` must be present, if token is not used and appRole/Secret is not used. (Vault username.)
- The environment variable `CASC_VAULT_APPROLE` must be present, if token is not used and U/P not used. (Vault AppRole ID.)
- The environment variable `CASC_VAULT_APPROLE_SECRET` must be present, it token is not used and U/P not used. (Vault AppRole Secret ID.)
- The environment variable `CASC_VAULT_TOKEN` must be present, if U/P is not used. (Vault token.)
- The environment variable `CASC_VAULT_PATHS` must be present. (Comma separated vault key paths. For example, `secret/jenkins,secret/admin`.)
- The environment variable `CASC_VAULT_URL` must be present. (Vault url, including port number.)
- The environment variable `CASC_VAULT_MOUNT` is optional. (Vault auth mount. For example, `ldap` or another username & password authentication type, defaults to `userpass`.)
- The environment variable `CASC_VAULT_NAMESPACE` is optional. If used, sets the Vault namespace for Enterprise Vaults.
- The environment variable `CASC_VAULT_FILE` is optional, provides a way for the other variables to be read from a file instead of environment variables.
- The environment variable `CASC_VAULT_ENGINE_VERSION` is optional. 
  If unset, your vault path is assumed to be using kv version 2. 
If your vault path uses engine version 1, set this variable to `1`.
- The issued token should have read access to vault path `auth/token/lookup-self` in order to determine its expiration time. 
  JCasC will re-issue a token if its expiration is reached (except for `CASC_VAULT_TOKEN`).

If the environment variables `CASC_VAULT_URL` and `CASC_VAULT_PATHS` are present, JCasC will try to gather initial secrets from Vault. 
However for it to work properly there is a need for authentication by either the combination of `CASC_VAULT_USER` and `CASC_VAULT_PW`, a `CASC_VAULT_TOKEN`, or the combination of `CASC_VAULT_APPROLE` and `CASC_VAULT_APPROLE_SECRET`.
The authenticated user must have at least read access.

You can also provide a `CASC_VAULT_FILE` environment variable where you load the secrets from a file.

File should be in a Java Properties format

```properties
CASC_VAULT_PW=PASSWORD
CASC_VAULT_USER=USER
CASC_VAULT_TOKEN=TOKEN
CASC_VAULT_PATHS=secret/jenkins/master,secret/admin
CASC_VAULT_URL=https://vault.dot.com
CASC_VAULT_MOUNT=ldap
```

A good use for `CASC_VAULT_FILE` would be together with docker secrets.

```yaml
version: "3.6"

services:
  jenkins:
    environment:
      CASC_VAULT_FILE: /run/secrets/jcasc_vault
    restart: always
    build: .
    image: jenkins.master:v1.0
    ports:
      - 8080:8080
      - 50000:50000
    volumes:
      - jenkins-home:/var/jenkins_home
    secrets:
      - jcasc_vault

volumes:
  jenkins-home:

secrets:
  jcasc_vault:
    file: ./secrets/jcasc_vault
```

==== Using environment variables (not recommended for secrets)

Although it is supported, it is not recommended to inject secrets using environment variables.
Doing so is *unsafe* because the environment variables can be read by
Jenkins admins and jobs running on the Jenkins controller.

You can use this to abstract away non secret configuration values across environments.

==== Using properties file

JCasC will try to resolve secrets via
link:https://en.wikipedia.org/wiki/.properties[.properties] file if
`/run/secrets/secrets.properties` exists. To change this
default file path you can use the environment variable `SECRETS_FILE`.
This file must be secured through machine ownership and permissions.

== External secret decryption (JWE)

External secret decryption allows administrators to define portable, encrypted secrets in JCasC configuration files. Secrets are encrypted externally using an RSA public key and decrypted dynamically during configuration resolution by Jenkins using a private key file.

Unlike instance-specific encrypted strings (`{AQAAAB...}`), external secret decryption is fully portable across multiple Jenkins controllers and environments that share or have access to the configured private key.

=== Architecture and format

The external decryption engine (`jwe`) implements hybrid encryption using **JSON Web Encryption (JWE) Compact Serialization** (link:https://datatracker.ietf.org/doc/html/rfc7516[RFC 7516]):

* **Content encryption (`enc`):** Secrets are encrypted symmetrically using **AES-256-GCM** (`A256GCM`) with a fresh, randomly generated 256-bit Content Encryption Key (CEK).
* **Key management (`alg`):** The CEK is wrapped (encrypted) asymmetrically using **RSAES-OAEP with SHA-256 and MGF1** (`RSA-OAEP-256`) with the recipient's RSA public key.
* **Key identification (`kid`):** The protected header must contain a key identifier (`kid`) matching one of the private keys loaded on the Jenkins controller.
* **Compact serialization:** The resulting JWE consists of 5 Base64URL-encoded parts separated by periods:
+
```text
<ProtectedHeader>.<EncryptedKey>.<InitializationVector>.<Ciphertext>.<AuthenticationTag>
```
+
This 5-part string is passed into the JCasC configuration using the syntax:
+
```yaml
${decrypt:jwe:<JWE_COMPACT_SERIALIZATION>}
```

IMPORTANT: The current implementation accepts only JWE Compact Serialization. Traditional direct-RSA encryption (such as raw ciphertext produced by `openssl pkeyutl -encrypt`) is not supported and will be rejected. OpenSSL command-line tools alone cannot assemble a JWE Compact Serialization structure; a dedicated JWE tool or library must be used.

=== 1. Key generation

Keys must be RSA key pairs with a minimum size of 2048 bits (3072 or 4096 bits recommended). Private keys must be stored in unencrypted PKCS#8 PEM format.

==== Generating an RSA private key

Generate a 3072-bit RSA private key in unencrypted PKCS#8 format:

```bash
openssl genpkey \
  -algorithm RSA \
  -pkeyopt rsa_keygen_bits:3072 \
  -out private-key.pem
```

==== Extracting the public key

Extract the corresponding RSA public key in standard X.509 SubjectPublicKeyInfo PEM format:

```bash
openssl pkey \
  -in private-key.pem \
  -pubout \
  -out public-key.pem
```

==== Converting an existing PKCS#1 private key

If you have an existing traditional PKCS#1 RSA private key, convert it to unencrypted PKCS#8 format using:

```bash
openssl pkcs8 \
  -topk8 \
  -nocrypt \
  -in old-private-key.pem \
  -out private-key.pem
```

==== Supported PEM format and key size requirements

* **Supported PEM marker:** Only unencrypted PKCS#8 keys beginning with `-----BEGIN PRIVATE KEY-----` and ending with `-----END PRIVATE KEY-----` are supported.
* **Rejected formats:** Traditional PKCS#1 keys beginning with `-----BEGIN RSA PRIVATE KEY-----` are not accepted directly and will cause decryption to fail with:
+
```text
Traditional PKCS#1 RSA keys are not supported. Please convert to PKCS#8 format.
```
* **Minimum key size:** Keys must be at least 2048 bits. Keys smaller than 2048 bits are rejected as insecure.

=== 2. Encryption procedure

To generate a JWE Compact Serialization compatible with `JweEncryptionEngine`, the encryption process must:

1. Generate a random 256-bit symmetric AES key (CEK).
2. Calculate the expected key identifier (`kid`) from the public key.
3. Construct a JWE protected header containing strictly:
   * `"alg": "RSA-OAEP-256"`
   * `"enc": "A256GCM"`
   * `"kid": "<calculated-kid>"`
4. Encrypt the plaintext secret with AES-256-GCM using the CEK.
5. Encrypt (wrap) the CEK with RSA-OAEP-256 using the recipient's RSA public key.
6. Assemble and output the 5-part JWE Compact Serialization string.

==== Key ID (`kid`) derivation

The `kid` header parameter is mandatory. The JCasC decryption engine derives the `kid` as follows:

1. Take the DER SubjectPublicKeyInfo encoding of the RSA public key (`publicKey.getEncoded()`).
2. Compute the SHA-256 message digest of these DER bytes.
3. Take the first 8 bytes of the digest.
4. Encode those 8 bytes using Base64URL without padding (`Base64.getUrlEncoder().withoutPadding()`).

You can calculate this `kid` using OpenSSL:

```bash
openssl pkey -in public-key.pem -pubin -outform DER | \
  openssl dgst -sha256 -binary | \
  head -c 8 | \
  openssl base64 -e | tr '+/' '-_' | tr -d '=\n'
```

==== Standalone encryption tool (Java / Nimbus JOSE + JWT)

Standard OpenSSL commands (e.g. `openssl pkeyutl`) produce raw RSA ciphertext, not JWE Compact Serialization. To generate compliant JWE strings, use a JOSE/JWE implementation such as link:https://connect2id.com/products/nimbus-jose-jwt[Nimbus JOSE + JWT].

Below is a complete, standalone Java encryption utility (`JweEncrypt.java`):

```java
import com.nimbusds.jose.EncryptionMethod;
import com.nimbusds.jose.JWEAlgorithm;
import com.nimbusds.jose.JWEHeader;
import com.nimbusds.jose.JWEObject;
import com.nimbusds.jose.Payload;
import com.nimbusds.jose.crypto.RSAEncrypter;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyFactory;
import java.security.MessageDigest;
import java.security.interfaces.RSAPublicKey;
import java.security.spec.X509EncodedKeySpec;
import java.util.Arrays;
import java.util.Base64;

public class JweEncrypt {
    public static void main(String[] args) throws Exception {
        if (args.length < 1) {
            System.err.println("Usage: printf '%s' \"<secret>\" | java -cp .:nimbus-jose-jwt-10.0.2.jar JweEncrypt <public-key.pem>");
            System.exit(1);
        }

        // 1. Read plaintext secret from standard input without adding newlines
        byte[] secretBytes = System.in.readAllBytes();
        if (secretBytes.length == 0) {
            System.err.println("Error: Empty plaintext secret provided.");
            System.exit(1);
        }
        String plaintext = new String(secretBytes, StandardCharsets.UTF_8);

        // 2. Load the RSA public key from PEM
        String keyPem = Files.readString(Path.of(args[0]));
        String base64Key = keyPem
            .replace("-----BEGIN PUBLIC KEY-----", "")
            .replace("-----END PUBLIC KEY-----", "")
            .replaceAll("\\s+", "");
        byte[] keyBytes = Base64.getDecoder().decode(base64Key);
        X509EncodedKeySpec keySpec = new X509EncodedKeySpec(keyBytes);
        KeyFactory keyFactory = KeyFactory.getInstance("RSA");
        RSAPublicKey publicKey = (RSAPublicKey) keyFactory.generatePublic(keySpec);

        // 3. Calculate key ID (kid): first 8 bytes of SHA-256 of SubjectPublicKeyInfo DER, Base64URL-encoded without padding
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] hash = digest.digest(publicKey.getEncoded());
        byte[] truncated = Arrays.copyOf(hash, 8);
        String kid = Base64.getUrlEncoder().withoutPadding().encodeToString(truncated);

        // 4. Construct JWE header with RSA-OAEP-256, A256GCM, and kid
        JWEHeader header = new JWEHeader.Builder(JWEAlgorithm.RSA_OAEP_256, EncryptionMethod.A256GCM)
            .keyID(kid)
            .build();

        // 5. Encrypt payload using RSAEncrypter
        JWEObject jweObject = new JWEObject(header, new Payload(plaintext));
        jweObject.encrypt(new RSAEncrypter(publicKey));

        // 6. Print the compact serialized JWE
        System.out.println(jweObject.serialize());
    }
}
```

=== 4. Private-key configuration and rotation

To allow Jenkins to decrypt JWE secrets, point Jenkins to the private key PEM file using either an environment variable or a Java system property.

==== Configuration methods

* **Environment variable:**
+
```bash
CASC_DECRYPTION_KEY_FILE=/run/secrets/casc/private-key.pem
```
* **Java system property:**
+
```bash
-Dcasc.decryption.key.file=/run/secrets/casc/private-key.pem
```

==== Precedence and missing configuration behavior

* **Precedence:** The system property (`casc.decryption.key.file`) takes precedence over the environment variable (`CASC_DECRYPTION_KEY_FILE`).
* **Unconfigured behavior:** If a configuration file contains a `${decrypt:...}` expression and neither the system property nor the environment variable is set, Jenkins throws an `IllegalStateException` upon attempting decryption, immediately aborting configuration reload:
+
```text
Decryption key file is not configured. Set either the system property 'casc.decryption.key.file' or the environment variable 'CASC_DECRYPTION_KEY_FILE'.
```

==== Key rotation using concatenated PEM files

To support zero-downtime key rotation without breaking existing encrypted secrets, the private key file can contain **multiple concatenated PKCS#8 PEM private-key blocks**:

```text
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQC... (Key 1)
-----END PRIVATE KEY-----
-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQC... (Key 2)
-----END PRIVATE KEY-----
```

When Jenkins parses the key file:
1. It reads each PEM block and calculates its corresponding `kid`.
2. When decrypting a JWE payload, it inspects the `kid` header parameter and selects the matching private key.
3. Older secrets encrypted with Key 1 continue to decrypt using Key 1, while new secrets encrypted with Key 2 decrypt using Key 2.

==== Dynamic key reload detection

The decryption engine checks the SHA-256 hash of the key file contents on disk during each decryption operation:
* If the key file content has changed (e.g. a new key was appended or an obsolete key removed), the engine automatically invalidates its cache and reloads the keys.
* Changes are detected during subsequent decryption operations without requiring a Jenkins restart or plugin reload.

=== 5. Size and format restrictions

The decryption engine enforces strict safety and format limits:

[cols="1,3",options="header"]
|===
| Parameter | Restriction / Constraint

| **RSA Key Size**
| Minimum **2048 bits**. Keys smaller than 2048 bits are rejected. 3072 or 4096 bits are recommended.

| **Key File Size**
| Maximum **64 KB** (65,536 bytes). This safely accommodates approximately 20 concatenated 4096-bit RSA keys for rotation while preventing memory exhaustion.

| **JWE Payload Length**
| Maximum **10 MB** (10,485,760 characters in the string payload). Payloads exceeding this character limit are rejected before parsing to prevent resource exhaustion.

| **Serialization Format**
| **JWE Compact Serialization only** (5 period-delimited Base64URL parts). JWE JSON Serialization is not accepted.

| **Key Management Algorithm (`alg`)**
| Must be strictly **`RSA-OAEP-256`**. Other algorithms (e.g., `RSA1_5`, `RSA-OAEP`, `ECDH`) are rejected.

| **Content Encryption Algorithm (`enc`)**
| Must be strictly **`A256GCM`**. Other encryption algorithms (e.g., `A128CBC-HS256`, `A128GCM`) are rejected.

| **Key ID (`kid`)**
| **Mandatory** in the protected header. Payloads without a `kid` are rejected.

| **Header Parameters**
| The protected header must contain **only** `alg`, `enc`, and `kid`. Compression (`zip`) and critical headers (`crit`) are explicitly rejected.

| **Plaintext Encoding**
| The decrypted payload must be valid **UTF-8**. Payloads with malformed or unmappable byte sequences fail decryption.
|===

==== Hybrid encryption vs. Direct RSA

Because this implementation uses hybrid encryption, RSA is only used to encrypt the 256-bit AES content-encryption key. The actual secret data is encrypted using AES-256-GCM. Consequently, the plaintext size limit of direct RSA encryption (~190 bytes for 2048-bit keys) does **not** apply. You can encrypt large text secrets (such as multi-line SSH private keys, TLS certificates, scripts) up to the 10 MB payload limit.

==== Binary secrets

The decryption engine returns a Java `String` decoded as UTF-8. If you need to store binary secrets (such as PKCS#12 certificates or binary keystores), Base64-encode the binary data before encrypting it into the JWE. In your JCasC configuration, combine `${decodeBase64:...}` with `${decrypt:...}`:

```yaml
${decodeBase64:${decrypt:jwe:<JWE_COMPACT_SERIALIZATION>}}
```

=== 6. Docker deployment example

When running Jenkins in Docker, mount the private key file from the host as a read-only file and set `CASC_DECRYPTION_KEY_FILE`:

```bash
docker run -d \
  --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  --mount type=bind,src=/host/secrets/casc-key.pem,dst=/run/secrets/casc/private-key.pem,readonly \
  -e CASC_DECRYPTION_KEY_FILE=/run/secrets/casc/private-key.pem \
  -e CASC_JENKINS_CONFIG=/var/jenkins_home/casc.yaml \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts
```

IMPORTANT: The host key file (`/host/secrets/casc-key.pem`) must exist before starting the container and must have restrictive permissions (e.g., `chmod 600` or `chmod 640`) while remaining readable by the container's Jenkins user (UID 1000 in official images).

=== 7. Kubernetes deployment example

In Kubernetes, store the private key in a dedicated Kubernetes `Secret` and mount it into the Jenkins controller Pod as a read-only volume.

==== Step 1: Create a dedicated Kubernetes Secret

Create the Secret containing the private key file:

```bash
kubectl create secret generic casc-decryption-key \
  --from-file=private-key.pem=/path/to/private-key.pem \
  --namespace jenkins
```

==== Step 2: Configure the Jenkins Deployment

Mount the Secret as a read-only volume in the Jenkins container and set `CASC_DECRYPTION_KEY_FILE`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: jenkins
  namespace: jenkins
spec:
  replicas: 1
  template:
    metadata:
      labels:
        app: jenkins
    spec:
      containers:
        - name: jenkins
          image: jenkins/jenkins:lts
          env:
            - name: CASC_DECRYPTION_KEY_FILE
              value: /run/secrets/casc/private-key.pem
            - name: CASC_JENKINS_CONFIG
              value: /var/jenkins_home/casc.yaml
          volumeMounts:
            - name: casc-decryption-key-volume
              mountPath: /run/secrets/casc
              readOnly: true
      volumes:
        - name: casc-decryption-key-volume
          secret:
            secretName: casc-decryption-key
            defaultMode: 0400
            items:
              - key: private-key.pem
                path: private-key.pem
```

==== Kubernetes RBAC and Security Guidelines

* **Keep private keys outside configuration repositories:** The private key material must never be committed to Git or embedded in JCasC YAML.
* **Restrict Secret access:** Use Kubernetes RBAC Role and RoleBinding resources to restrict read access to the `casc-decryption-key` Secret so that only cluster administrators and the Jenkins controller service account can read it.

=== 8. Threat model and security considerations

Administrators must understand the security boundaries of external secret decryption:

* **Private key protection:** The private key file must be protected with strict filesystem permissions (e.g., `chmod 400` or `chmod 600`), accessible only by the Jenkins controller process and trusted system administrators. Never commit private keys to version control.
* **Trust model for configuration authors:** Anyone who has permission to modify or submit JCasC configuration files must be trusted with access to all secrets decryptable by the controller's private key.
* **Global variable interpolation context:** Decryption is executed during general variable interpolation across all configuration fields and is **not restricted** to fields of type `hudson.util.Secret`.
+
WARNING: If an untrusted user is able to edit the JCasC configuration, they could place `${decrypt:jwe:...}` into an ordinary text field (such as `jenkins.systemMessage` or an agent description). Jenkins will decrypt the secret and display it in plain text in the Jenkins web UI, system logs, or REST APIs.
* **Encryption at rest vs. runtime memory:** JWE encryption protects secrets at rest in configuration repositories, Git history, and CI/CD pipelines. It does not protect secrets once decrypted in Jenkins runtime memory. Once loaded into Jenkins, secrets are handled according to Jenkins core credential security rules.

=== 9. Decryption failure behavior

Decryption failure behavior differs significantly from ordinary variable resolution:

* **Always aborts configuration reload:** If a `${decrypt:...}` expression fails to evaluate for any reason, JCasC immediately throws an `IllegalStateException` and aborts configuration application completely. The previous working configuration remains active.
* **Strict mode setting is ignored for decryption failures:** Unlike missing `readFile` or `sysProp` lookups (which log a warning and fall back to an empty string `""` when `CASC_STRICT_SECRET_RESOLUTION=false`), decryption failures **always** fail hard and never fall back to an empty string or default value.
* **Typical causes of decryption failure:**
  - Key file missing, unreadable, or exceeding 64 KB.
  - No private key in the file matches the `kid` in the JWE header.
  - Invalid JWE format or unsupported header parameters (e.g. missing `kid`, compression enabled, algorithms other than `RSA-OAEP-256` / `A256GCM`).
  - Corrupted or modified ciphertext (AES-GCM authentication tag verification failure).
  - Ciphertext encrypted with a public key that does not match the configured private key.
  - Decrypted payload contains invalid UTF-8 bytes.

=== 10. End-to-end workflow summary

[cols="1,2,3",options="header"]
|===
| Step | Action | Command / Example

| **1. Generate Key Pair**
| Generate private key and extract public key.
| `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out private-key.pem` +
`openssl pkey -in private-key.pem -pubout -out public-key.pem`

| **2. Encrypt Secret**
| Encrypt secret plaintext into JWE Compact Serialization.
| `printf '%s' "my-secret" \| java -cp .:nimbus-jose-jwt-10.0.2.jar JweEncrypt public-key.pem`

| **3. Configure JCasC YAML**
| Reference the secret using `${decrypt:jwe:...}`.
| `secretPassword: "${decrypt:jwe:eyJraWQiOi...}"`

| **4. Deploy Private Key**
| Mount `private-key.pem` and point Jenkins to it.
| Set `CASC_DECRYPTION_KEY_FILE=/run/secrets/casc/private-key.pem`

| **5. Apply Configuration**
| Start or reload Jenkins.
| JCasC automatically decrypts secrets using the matching key.
|===

== Passing credentials as encrypted text

This is an additional engine which uses the link:https://javadoc.jenkins-ci.org/hudson/util/Secret.html[hudson.util.Secret] engine to define encrypted credentials in JCasC configuration files.

* Encrypted credentials can be stored in plain text
* Encryption is done using the Jenkins-internal secret key
  which is unique for every Jenkins instance.
  It means that the credentials are not portable between instances.
* Encrypted credential values can be exported using the link:./configExport.md[configuration export] feature.

NOTE: For portable encrypted secrets that can be decrypted across different Jenkins controllers using an RSA key pair, see <<external-secret-decryption-jwe,External secret decryption (JWE)>>. (See also link:https://github.com/jenkinsci/configuration-as-code-plugin/issues/1141[JCasC #1141]).

Configuration example:

```yaml
credentials:
  system:
    domainCredentials:
    - credentials:
      - usernamePassword:
          id: "exampleuser-creds-id"
          username: "exampleuser"
          password: "{AQAAABAAAAAQ1/JHKggxIlBcuVqegoa2AdyVaNvjWIFk430/vI4jEBM=}"
          description: "Sample credentials of exampleuser"
          scope: GLOBAL
          
```

=== Strict Secret Resolution

By default, if a secret variable cannot be resolved, JCasC will log a warning and replace the variable with an empty string. If you are using a remote secrets engine, this can result in credentials being unexpectedly overwritten with empty values during a configuration reload.

To prevent this, you can enable **Strict Secret Resolution**. When enabled, any unresolved secret that does not have a defined default value (using the `:-` operator) will cause the configuration reload to abort entirely, leaving the previous working configuration intact.

You can enable this by setting the following environment variable or Java system property:

* **Environment Variable:** `CASC_STRICT_SECRET_RESOLUTION=true`
* **System Property:** `-Dcasc.strict.secret.resolution=true`
